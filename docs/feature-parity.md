## 0. 怎麼算的（口徑，先讀這段）

1. **三家共有 ✅ 的判定**：同一功能必須在 **三份檔里都找得到對應證據**（Element 欄←`element.md`；SchildiChat 欄＋FluffyChat 欄←`fluffy-schildi.md`）。缺一邊就不標 ✅，一律改列到第二張表「非三家共有，僅供參考」。
2. **SchildiChat 有兩條線**（web＝Element fork、android＝Element Android fork）：**任一條命中即算 SchildiChat 有**，證據欄以 `web:`／`android:` 前綴註明是哪一條線（沿用 `fluffy-schildi.md` C-1 表的寫法）。若某家只有「語意部分重疊」的證據（該檔的 `[WA]`／`△` 標記），本表仍在「三家共有?」欄保留 ✅ 但**括號註明偏差不另立符號**，現僅 3 條（A′-12、B-08、B-11，見 §5）。
3. **Nashira 欄只准取自 `nashira.md`**，符號：
   - ✅＝該檔以實物證據肯定存在（附其檔案＋行號）
   - 🟥＝該檔標為「半成品／假完成」（程式碼在但畫面接不上、或只做一半）
   - ❌＝該檔**明寫**「未找到／零命中」
   - ➖**未盤到（需查）＝該檔完全沒提這件事**。此種條目**一律不下「沒有」的結論**，只在括號裡補註「不在 §一 的 29 項設定清單／`C/App.kt:252-291` 的 26 鍵存檔快照內」這類**可核對的列舉事實**。
4. **主表排序**（同一張表，用序號前綴分組）：
   `A`＝三家共有 ✅ 且 Nashira **明寫 ❌（完全沒有）** → `A′`＝三家共有 ✅ 但 Nashira **未盤到** → `B`＝三家共有 ✅ 且 Nashira **🟥 半成品** → `C`＝三家共有 ✅ 且 Nashira **✅ 已有（只需核對細節）**；最後才是兩家有的參考表。分組說明：`A′` 是用戶交付要求之外補的一層，避免把「沒盤到」寫成「沒有」。
5. **「缺什麼」欄的語意**：一定寫明是「**資料層在、缺 UI**」還是「**完全沒有**」，並保留 `nashira.md` 给的行號。
6. **成本（小／中／大）**＝本輪主觀估值：小＝純 UI／接線、中＝要新增事件型別或跨平台 expect/actual、大＝要動 SDK 能力、加密協定或整頁新功能。
